## The one question

Does our host-authoritative, launch-parameter-only sync model coexist with **continuously synced
free-roaming avatars**? `Docs/Networking.md` is 34 lines and says nothing about roaming;
`FirstPersonController.cs` says in its own header that it is deliberately not networked. That gap
is the entire reason this spike exists. Everything else is out of scope.

Secondary question: does replaying a throw from `LaunchParameters` on two machines drift enough to
matter, and does the "host confirms pin state, everyone snaps" mitigation actually hold?

## Order of work — stop at every STOP

**Step 0 — Plan only.** Restate the question in your own words. List your assumptions. List every
file you will add or change. List the exact editor clicks I will have to do. Then **STOP** and wait
for my go-ahead.

**Step 1 — Mirror install.** You cannot install it; I do. Tell me exactly how (Asset Store vs GitHub
release, which one you recommend and why, and whether it should be committed to the repo or ignored
given our Git LFS setup). Then verify it compiles and report the version. **STOP.**

**Step 2 — Bare connection.** NetworkManager + the KCP transport in the spike scene. Host and client
connect over localhost. Nothing else — no avatars, no bowling. **STOP, I test.**

**Step 3 — Networked roaming.** `PlayerAvatar` gets a NetworkIdentity and real ownership; roaming
movement replicates. Address this specifically: `PlayerAvatar.IsLocal` is currently a plain public
bool defaulting to `true`, which is **fail-open** under Mirror — every avatar would consider itself
local. Propose the fail-closed wiring and show me how the existing `ControlMode` state machine
behaves when mode changes have to replicate. **STOP, I test.**

**Step 4 — One networked throw.** Active client sends `LaunchParameters` to the host as a Command;
host broadcasts it; both sides replay the throw locally from those parameters; host confirms the
resulting pin state and everyone snaps to it. Measure and report the drift you actually observe
between the two machines — PhysX is not bit-deterministic and I want the real number, not the
theory. Run `/qa-review` before you call this working. **STOP, I test.**

**Step 5 — Findings.** Write `Docs/spikes/2026-08-XX-mirror-kcp-findings.md`: what worked, what
drifted, what roaming sync actually cost in bandwidth and complexity, whether the walkable-alley
design survives contact with the netcode, and what `Docs/Networking.md` needs to say about roaming
that it currently doesn't. Then tell me explicitly which parts of the spike to throw away and which
are worth keeping.
